# ScummVM hybrid core for MiSTer (ScummVM)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `ScummVM` (the engine: core, folders `games/dnk/ScummVM/` and `logs/dnk/ScummVM/`, `_Other/dnk/dnk-ScummVM_*.rbf`, release), `scummvm` (game submodule, binary in `build/`, log, lock). The games and their menu entries (`_Other/dnk-<title>.mgl`): `package/games.txt` (in the zip as `games/dnk/ScummVM/games.txt`, from which the database's build makes the launcher's catalogue).
- The game is the `scummvm/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Release: **no zip on GitHub** (Danik, 2026-10-28): the zip is about 192 MB and GitHub refuses a file over 100 MB, so `releases/` stays empty and a release is the commit and push alone; the zip stays in `dist/` on the build PC. Players get every file through the database, which stores them one by one (the largest, the icon pack 61 MB and the program 55 MB, are under the limit; GitHub warns above 50 MB). Publish from `dist/`, only when Danik asks: `hybrid/launcher/distribution.py publish ~/dnk_Distribution_MiSTer dist/ScummVM_YYYYMMDD.zip` (the rule in `hybrid/CLAUDE.md`). Every build puts the program into the database's history again: keep an eye on its size.
- Try a build on the MiSTer without installing it: `MISTER=root@<address> tools/test_on_mister.sh <id>|list|nodata|log|stop` (the rule in `hybrid/CLAUDE.md`).
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

## Decisions (Danik, 2026-10-24)

- **One menu entry, ScummVM's own launcher.** `package/games.txt` has the one line `ScummVM|ScummVM`; no set names, no curated games, no per-game MGLs. Players copy each game's folder into `games/dnk/ScummVM/` (or its USB copy) and add it with ScummVM's *Add Game* / *Mass Add*; the browser starts in `DATADIR`. So the missing-data rule has nothing to check: an empty launcher is the start, and the README says where games go. OSD settings and button mappings are the core's (one `ScummVM.CFG`); per-game settings are ScummVM's own (`scummvm.ini` in `DATADIR`, saves there too).
- **Source**: ScummVM v2026.4.0 (GPL-3.0-or-later). The repository is [ItsDanik/ScummVM_MiSTer](https://github.com/ItsDanik/ScummVM_MiSTer) (public, 2026-10-28); the `scummvm/` submodule is the fork [ItsDanik/scummvm](https://github.com/ItsDanik/scummvm), branch `mister`.
- **Engines**: every 2D engine that is on by default and needs no OpenGL, built into the one binary (69 MB unstripped; Linux maps its pages as they are used), without the 3D ones and the heavy FMV or bigger-than-640x480 ones (`ENGINES_OFF` in `build.sh`: Zork Nemesis / ZGI, Blade Runner, Riven, Titanic, Myst 3, Broken Sword 2.5, Wintermute, Nancy Drew, ...). Dynamic plugins only if memory or start time turn out to need them. Plus `grim` (Grim Fandango) with its TinyGL software renderer, as an early benchmark: if it cannot hold a usable rate at 640x480i, say so to Danik before shipping it. The README calls Grim Fandango built in but slow and experimental and leaves its pad controls out for now (Danik, 2026-10-28). **`monkey4` (Escape from Monkey Island) is off** (Danik, 2026-10-28: "experimental and incomplete upstream as well"; `--disable-engine=monkey4` in `build.sh`, and its games are not detected either, `MISTER_HYBRID` in `engines/grim/detection.cpp`: upstream finds them and only refuses to start them; the README lists it as not built in); it was on from 2026-10-27, never tried on the MiSTer, and the work done for it stays in the fork (the note in *Status*). Broken Sword 2.5 (`sword25`) stays off: it draws only at 800x600 (`initGraphics(800, 600)`). Parser / keyboard games (AGI, SCI0, Glk) are built in and run from the launcher; the README says they are best with a keyboard.
- **Video**: the window is the game's size, 1x, no scaler, no aspect correction. 320x200 games in 320x200; 640x480 in 640x480i, 640x400 in 640x400i; other sizes centred in the smallest mode they fit. ScummVM's GUI (launcher, Global Main Menu) at the game's resolution: lowres layout at 320x200, no mode switch when it opens. The launcher (no game running) is 320x200 by default, or 640x480i with ScummVM's highres layout by the OSD's *Launcher* line (Danik, 2026-10-25; `MisterGraphicsManager::initSize()` gives the launcher that size, and the switch is live while the launcher shows, else at the return to it). **Host version 18** (2026-10-28): the launcher (no game running) takes a frame at every field of 480i (`MH_SetFieldRate()` in `MisterGraphicsManager::initSize()`, on while `g_engine` is null): 60 pictures a second on a CRT instead of 30, as dnkLauncher; a game, and ScummVM's Global Main Menu over it, at the game's rate (a frame every second field in 480i). The core has the *Flicker Filter* (`FLICKER` 1; Light, the default (Danik, 2026-10-28), Strong or Off on *CRT Options*, greyed out while not interlaced), which filters the launcher at 640x480 and the 640x400 / 640x480 games alike; nothing in ScummVM for it. The USER button and the OSD's *Reset* start ScummVM again (the template's launch script, exit code 44). **No 240-line mode and no HUD lines**: the games' backgrounds and verb bars are fixed 200-line art (and the hires games 480 lines already), so nothing can fill 240 lines; `HUD_EDGES` none.
- **Backend**: `backends/platform/sdl/mister/` (`--host=mister`, or `--backend=mister` for the PC build; `MISTER_HYBRID`) on top of ScummVM's SDL/POSIX backend and `hybrid/sdl2`: `MisterGraphicsManager` makes the SDL window the game's size and draws into its RGB565 surface (no renderer), the cursor drawn in, CLUT8 converted (INDEX8 later as an optimisation); frames paced by `SDL_MISTER_VSYNC=1`. Data files (themes, engine data, virtual keyboard) in `data/` next to the program.
- **Music**: `MIDI_SYNTH` 1. *Music* = MIDI: General MIDI to the synthesizer (ScummVM's MT-32-to-GM mapping where a game has MT-32 music only); native MT-32 to an MT32-pi that is on in MT-32 mode. *Music* = FM chip: AdLib through a new OPL type writing `MH_FMWrite()` from a silent mixer stream (exact audio frames); OPL3 / dual OPL2 games fall back to DOSBox's OPL on the ARM. The MIDI driver is a `MidiDriver_Emulated` (exact `ahead`), keeps every channel's state to send again after `MH_MidiSynthChanged()`, and holds a song's start back by `MH_MidiBacklog()`. **Exception to the framework's rule**: the MIDI / FM switch takes effect at the next game start (engines pick their driver once; Danik, 2026-10-28: no live switch, no three-way line), and a change of the OSD line while a game runs says so over the game ("Music: FM chip from the next start of the game", ScummVM's on-screen message, `applyOSD()`); the Pi / synthesizer switch is live. No Munt.
- **Controls** (`J1`): stick and d-pad move the pointer (below); A left click, B right click, X Esc (skip cutscene), Y `.` (skip line), L held slow pointer, R F5 (game's menu), Select virtual keyboard, Start Global Main Menu (Ctrl+F5). *Menu OK* / *Menu Back* are Enter / Esc in ScummVM's GUI. An engine's own pad keymap (Grim's tank controls) wins while it runs. No rumble, triggers or stick clicks.
- **The pad's pointer** (2026-10-30, a player's report: "the mouse calibration when using a controller ... is pretty bad"; not yet tried on a real pad; the numbers at 320x200, measured against `fakecore`). Upstream's virtual mouse has one value for the stick and the d-pad, and Main_MiSTer presses the d-pad as well when the stick is past half way (`dpad_threshold` 50): at 60% the pointer ran at full speed, and back at 45% it stood still with the stick held; a tap of the d-pad moved it 30 pixels, and the engines' d-pad actions came with the stick (Drascula's save menu with the stick to the right, Queen's inventory, Touche's text and voice). Now (`MISTER_HYBRID` in `virtual-mouse.cpp`): the stick's speed goes with the square of its tilt (35 pixels a second at 40%, 92 at 60%, 46 at 45%, 295 at full), the d-pad apart (`VMOUSEDPAD*`: a tap two pixels (Danik, 2026-10-30), one with Slow Pointer held, held a pause of 150 ms and then up to full speed in 850 ms), the pointer stops at the last pixel (319, was 320). **It moves once before every frame shown** (Danik, 2026-10-30: "check if it is updated once every frame"; `MisterGraphicsManager::updateScreen()`, `VirtualMouse::movePointer()`), by the fields counted between the last two frames (read just after a frame: before one the counter may just have ticked or not), and the game hears at its next poll: moved at the polls, Lure's 50 Hz on 59.6 frames stood still every fifth frame and went twice as far on the next (per frame 3 3 0 4 5, now 3 3 3 2 3, as the launcher at 320x200 and 640x480i). `warpMouse()` throws away what is queued and polls the sources again: `_warping`, and during a stroke the move goes from the last move, not `getMousePos()`, so an engine's own warp while the stick is held is overridden until 6 fields after the stroke. `MisterEventSource::isStickDpad()` stops the d-pad press that is the stick's while the pointer is on the screen; with it hidden the press goes through (Grim walks with the stick, as other games without a pointer). The real d-pad keeps the engine's actions: in Lure, Drascula and others it does not move the pointer, the stick does. The drawn pointer's tip is where the clicks land (a shot at the logged position), so nothing was wrong there.
- **A and B and Menu OK / Back** (2026-10-30, Danik: "A and B buttons seem to press things simultaneously (dialogs appear and close immediately)"). Every PlayStation or Xbox pad without a mapping has the bottom button Menu OK and the core's B, the right one Menu Back and the core's A, and the library reads Menu OK / Back from Linux, ahead of the core's buttons: "an action is held" was not true yet, so in a game the bottom button was a left click with the right click, the right one Esc with the left click, and in the GUI Esc or Enter with the click. Now by `MH_MenuButtons()`, whatever comes first: in a game such a button is its action alone; in ScummVM's GUI, by the rule of 2026-10-17 (the menu does what Menu OK says), it is Menu OK alone, a click at the pointer, or Menu Back alone, Esc, nothing in the launcher (`isMenuAction()` stops the action). So on such a pad the bottom button clicks and the right one closes in the GUI, and in a game A (the right one) clicks. Checked on the PC against `fakecore` with the Menu button a field ahead of the action, by a temporary line (the PC cannot read `/dev/input`): Global Options opened and stayed, closed by Menu Back; Drascula's inventory (the right click) stayed open, no quit prompt.
- **OSD game options** (from bit 24): *Pointer Speed*, *Stick Deadzone* (bits 36:35, Normal / Small / Large: `joystick_deadzone` 3 / 1 / 6), *Launcher* (bit 34: 320x200 / 640x480), *Speech Volume*, *Subtitles* (Game default / Speech only / Subtitles only / Both, over every game's setting), *Text Speed* (bits 39:37, Normal / Slowest / Slow / Fast / Fastest: `talkspeed` the game's / 0 / 30 / 128 / 255); *Sound Volume* / *Music Volume* are ScummVM's SFX and music volumes. All of them in ConfMan's transient domain (`applyOSD()`), over the games' and the global settings.
- **Options dialogs** (Danik, 2026-10-28, from the review page of the options): ScummVM's tabbed Global Options, Game Options and in-game Options are replaced by `MisterOptionsDialog` (`gui/mister-options.cpp`, `MISTER_HYBRID`): one list in categories (pink headings, the theme's override colour), labels right-aligned before their boxes, a scrollbar when it is longer than the window, Cancel / OK, the same lines at 320x200 (a label too wide for its column goes on a line above its box). Its layouts are made in code (`defineLayouts()`), so they work with every theme. Global ("MiSTer ScummVM Options"): *Interface* (Theme, GUI language, the GUI in the game's language, kinetic scrolling), *Leaving a game* (return to the launcher, confirmation on exit), *Saving* (Autosave), *Music* (Roland GS mappings (experimental), `enable_gs`). A game's (titled with its name): *This game* (Name, ID shown and not changeable, Game Path), *Game options* (the engine's own), *Picture* (Render mode, only for a game with modes), *Hotspots* (the three lines), *Music* (Roland GS: As in Global Options / On / Off, only for a game with MT-32 or GM music). In-game (from the Global Main Menu, and where an engine opens ScummVM's options from its own menu: `ConfigDialog::runModal()`): the engine's own options alone; the Global Main Menu has no *Options* button for an engine without any it can change while it runs. Everything else is hidden: keymaps, volumes and Mute all, music devices, the AdLib emulator (the FM chip), text and speech (the OSD), pointer speed, MIDI and MT-32 lines but GS, paths, GUI scale and renderer, font scaling (stays off), debug level, language and platform of a game. `mister_full_options=true` in `scummvm.ini` brings ScummVM's own dialogs back. Of ScummVM's themes only Modern is shipped beside ours (`package.sh`), and the theme browser leaves out the built-in one.
- **Cheats page**: *Fast Mode* Off / Fast / Turbo (SCUMM's Ctrl+F / Ctrl+G), greyed out (`MH_SetMenuMask()`) while another engine runs. Nothing else: the engines' other cheats are debugger commands with arguments.
- **Game icons** (Danik, 2026-10-25): every pack of ScummVM's icons (downloads.scummvm.org `frs/icons/`, 12 packs, 375 MB; GPL-2.0, scummvm-icons' LICENSE and AUTHORS next to them), merged into one pack by `tools/make_icons.py` (the newest pack's icon of a game wins, as in ScummVM; 752 icons; the newest pack's `games.xml`, `companies.xml`, `series.xml`, `engines.xml` too, which *Group by* Publisher / Series / Year and the artwork view read), each icon made in the sizes the launcher draws it at, so ScummVM only decodes it (the 512x512 icons made the launcher's start slow and its scrolling jerky on the MiSTer; with them made for the size it starts at once): `icons/` 99x99 (the grid at 4 a row in 640x480, inside the margin for CRTs), `icons143/` (3 a row), `icons236/` (the artwork view, JPEG on the theme's background); 61 MB, stored. The grid takes `icons<size>/` where its thumbnails have that size, else `icons/` scaled, and loads nothing before its layout gives the size (ScummVM decoded every visible icon a first time at size 0; `MISTER_HYBRID` in `gui/widgets/grid.cpp`). Palette and grey icons, which the grid skipped, are converted. **At least 3 icons a row** (Danik: "let's make it fast", then 3): the launcher's slider starts at 3 (`gui/launcher.cpp`, `MISTER_HYBRID`), and the backend raises a smaller `grid_items_per_row`. `tools/icons.sh` fetches the packs at pinned SHA-256 sums into `build/icons/` and makes the merged pack when it, `make_icons.py` or `make_theme.py` (the artwork's size and background) changes (`package.sh` runs it; never committed); it goes to `games/dnk/ScummVM/icons/`, the backend's `iconspath` (`getDefaultIconsPath()`, not `$HOME/.cache`). ScummVM has the grid only in its high resolution layout, so the icons show with *Launcher* at 640x480, at 320x200 it is the list.

## Status (2026-10-25)

- Tested on the PC with `fakecore` (PC build, `./build.sh host`): the start and logo, ScummVM's launcher at 320x200, Lure of the Temptress at 320x200, the Fate of Atlantis demo with FM music (the core's chip) and with MIDI music (the synthesizer, GeneralUser GS), the pointer on the d-pad, Start (Global Main Menu) and Menu Back (closes it), the OSD's Fast Mode (Turbo). Free games for tests: downloads.scummvm.org (`frs/extras`, `frs/demos`), never committed.
- Danik installed the 2026-10-25 build on the MiSTer and found Grim Fandango below 10 fps. Still to do there: `tools/test_on_mister.sh` (`ScummVM`, `list`, `nodata`), Menu OK / Back on buttons with actions, the MT32-pi, music volume on the FM chip and the synthesizer (ScummVM applies *Music Volume* through the engines' own MIDI volume; check it reaches both), the `DRAW_AHEAD` benchmark of the framework rule (ScummVM paces with `SDL_MISTER_VSYNC`, no `MH_PresentAtField()` yet).
- **Grim Fandango on the MiSTer** (2026-10-25, Windows CD, Manny's office, 640x480i): was 5.7 to 9.5 fps (TinyGL's dirty rectangles on: 92 to 143ms a frame to draw once anything moved). Now about 21 fps standing, 14 to 19 walking, 13 with Manny filling a third of the screen. What did it, all measured on the MiSTer with `MISTER_PROF` (below): `dirtyrects` off by default (`mister.cpp`); textures point sampled, as the original's software renderer (`MISTER_HYBRID` in `engines/grim/gfx_tinygl.cpp`; bilinear filtering was most of Manny's time); in TinyGL (`graphics/tinygl/`, for every platform): an opaque colour-keyed image kept in the frame buffer's format, a fast textured span for RGB565 with 32-bit textures (`putTexturedSpanFast()`: z test, nearest texel, Gouraud, alpha test; compared span by span with the generic code, 5.7 million spans, none different), the stencil-only fill of Grim's shadows as a `memset`, a clear left out where blits overwrite it, and the frame's first draw calls (the base: background, z buffer image, the room's parts in front) drawn again only where the last frame drew over them (`presentBufferSimple()`; whole frames drawn both ways and compared, none different); in the backend: the window surface is the library's buffer (`SDL_MISTER_DIRECT`), ScummVM's `_tmpscreen` copy skipped, and only what changed in the last two frames copied (`MISTER_HYBRID` in `surfacesdl-graphics.cpp`; the shown buffer compared with ScummVM's screen, 1300 frames, none different). Left: the textured span itself (about 30% of a walking frame, bound by instructions; ARM instead of Thumb-2 made no clear difference), TinyGL's command side (about 15%), the shadow pass with the stencil test (about 6%). `grim` stays: Danik decides whether this is usable.
